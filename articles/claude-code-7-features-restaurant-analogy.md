## はじめに

この記事では、Claude Code の7つの拡張機能である **CLAUDE.md・.claude/rules/・Skills・Sub-agents・MCP・カスタムコマンド・Hooks** について、それぞれの役割と使い分けを解説します。

Claude Code を触っていると、こんな状態になりませんか。

> CLAUDE.md、.claude/rules/、Skills、Sub-agents、MCP、カスタムコマンド、Hooks…… 名前は知ってるけど、結局どれをどの場面で使うのか分からない。

機能が7つもあると、最初は全部似たものに見えてしまいます。

今回の記事では、これらは7つの機能を解説していきます。

## この記事の対象読者

- Claude Code を使い始めて、機能の多さに戸惑っている方
- CLAUDE.md は知っているが、他の機能との使い分けが分からない方
- 7つの機能を一度に整理したい方

逆に、各機能の詳細な設定方法やベストプラクティスを深掘りしたい方には物足りないかもしれません。この記事は「全体像を把握する」ことを目的としています。

## 2つの軸で整理する

### 軸1：いつ読み込まれるか

| タイミング | 機能 |
| --- | --- |
| 常に（起動時から） | CLAUDE.md |
| 条件付き（特定ファイルを触ったとき） | .claude/rules/ |
| 条件付き（イベント発火で必ず） | Hooks |
| 必要なときだけ（Claudeが判断） | Skills |
| 必要なときだけ（こちらが依頼） | Sub-agents |
| 必要なときだけ（外部連携が要るとき） | MCP |
| 手動（こちらが叩く） | カスタムコマンド |

### 軸2：誰が実行するか

| 実行者 | 機能 |
| --- | --- |
| Claude本体 | CLAUDE.md / .claude/rules/ / Skills / カスタムコマンド |
| 別プロセス（独立したコンテキスト） | Sub-agents |
| 外部のシェルコマンド | Hooks |
| 外部サービス | MCP |

**「Claude本人の知識・ルールを増やす」グループ** と、**「外部の誰か（別プロセス・シェル・サービス）に任せる」グループ** に大別できます。この2グループを意識するだけで、選択肢がかなり絞れます。

## 各機能の詳細

### CLAUDE.md：常時読み込まれるプロジェクトルール

Claude Code の **起動時に自動で読み込まれる** ファイルです。一度書いておけば、毎回「インデントはスペース2つ」「コミットメッセージは日本語で」と説明しなくて済みます。

```markdown
# プロジェクト共通ルール

- インデントはスペース2つ
- コミットメッセージは日本語で書く
- 実装にはテストを必ず添える
- 外部ライブラリを追加する前に一声かける
```

**向いている内容**

- コーディング規約（命名規則、インデントなど）
- 禁止事項（使ってほしくないライブラリなど）
- アーキテクチャの基本方針

**注意点：** 何でも書くと肥大化します。Markdown を書いているときに「TypeScript の規約」まで毎回読み込まれるのは無駄です。「全ての作業で常に守るべきこと」だけに絞るのがコツです。

### .claude/rules/：ファイルパスに紐づいたルール

CLAUDE.md の肥大化を解消する仕組みです。`paths` で対象ファイルを指定すると、**そのファイルを操作したときだけ** ルールがコンテキストに足されます。

```markdown
---
paths: src/api/**/*.ts
---

# API 開発ルール

- 全エンドポイントで入力バリデーションを必須にする
- エラーレスポンスは共通フォーマットに揃える
- 認証が必要な経路には必ずミドルウェアを通す
```

この例だと、`src/api/` 配下の TypeScript を触ったときだけこのルールが効きます。フロント側のファイルを編集している間は読み込まれません。

**向いている内容**

- フロント／バックで分かれるルール
- 特定ディレクトリ固有の規約
- ファイル種別ごとの設定

### Skills：Claudeが必要と判断したときだけ読み込む知識

Skills は、Claude が「この知識が要る」と判断したときだけ本体が読み込まれます。普段は名前と説明（description）だけが常駐しているので、コンテキストを圧迫しません。

```markdown
---
name: frontend-design
description: フロントエンドのデザイン規約。UI実装やコンポーネント作成のときに参照する。
---

# デザインルール

## カラーパレット

- Primary: #3B82F6
- Secondary: #10B981

## 余白

- 基本単位は 4px。8の倍数を優先する。
```

「ログイン画面のUIを作って」と頼むと、Claude が自分で `frontend-design` を参照して作業してくれます。

**向いている内容**

- デザインシステムのガイドライン
- 特定技術のベストプラクティス
- 重要だが参照頻度は高くない知識

**注意点：** description が曖昧だと、必要なときに読み込まれません。「何ができて、いつ使うのか」を具体的に書くことが重要です。

### Sub-agents：独立したコンテキストで動く別プロセス

Sub-agents は、メインの Claude とは **別のコンテキスト** で動きます。大量のファイルを読んで調査しても、メインの会話履歴は増えません。返ってくるのは結果のサマリーだけです。

```markdown
---
name: code-reviewer
description: コード品質とセキュリティをレビューする。実装の区切りで委譲する。
tools: Read, Grep, Glob, Bash
---

あなたはシニアコードレビュアーです。
変更点を読み、バグ・セキュリティリスク・可読性の観点で指摘してください。
```

**向いている内容**

- 大規模なコードベースの調査
- セキュリティ・パフォーマンスなど専門的なレビュー
- メインの会話を汚したくない重い処理

**注意点：** Sub-agent はメインの会話の文脈を知りません。必要な情報は依頼時に明示的に渡す必要があります。

### MCP：外部ツール・DB・APIへの接続口

MCP（Model Context Protocol）は、Claude Code を外部ツール・DB・API とつなぐ仕組みです。ここまでの機能が「Claudeの知識」を増やすものだったのに対し、MCP は **外部サービスへのアクセス** を担当します。

```bash
# GitHub と連携する
claude mcp add --transport http github https://mcp.github.com

# ローカルのスクリプト経由で DB と連携する
claude mcp add --transport stdio postgres -- python postgres-mcp.py
```

**向いている内容**

- データベースへの直接アクセス
- 外部API連携（GitHub、Slack など）
- ファイルシステム以外のリソース操作

**注意点：** 設定に技術的な知識が必要です。ネットワークや認証エラーなど外部依存のトラブルも起き得ます。

### カスタムコマンド：よく使うプロンプトをコマンド化

よく使うプロンプトを `/コマンド名` で呼び出せるようにする仕組みです。「main との差分を見てコミットメッセージを提案して」を毎回打つ手間が消えます。

```markdown
---
allowed-tools: Bash(git add:*), Bash(git commit:*)
argument-hint: [commit message]
---

## 状況

- 現在のステージング状態: !`git status`
- 差分: !`git diff HEAD`

## やること

上記の変更内容から適切なコミットメッセージを作り、コミットを実行してください。
```

**向いている内容**

- コミット作成
- テスト実行
- デプロイ準備

**注意点：** Skills と違って自動では呼ばれません。`/commit` のように、こちらが明示的に叩く必要があります。

### Hooks：ライフサイクルイベントに紐づく自動実行

特定のライフサイクルイベントが起きたときに **必ず実行される** シェルコマンドです。Claude が判断するのではなく、条件が満たされれば例外なく走る決定論的な仕組みです。

| イベント | 発火タイミング |
| --- | --- |
| SessionStart | セッション開始時 |
| PreToolUse | ツール実行の前 |
| PostToolUse | ツール実行の後 |
| Stop | タスク完了時 |

設定は `.claude/settings.json` に書きます。

```json
{
  "hooks": {
    "PostToolUse": [
      {
        "matcher": "Edit|Write",
        "command": "npx prettier --write $CLAUDE_FILE_PATH"
      }
    ]
  }
}
```

これでファイルを編集・作成するたびに、自動で Prettier が走ります。

**向いている内容**

- 編集後の自動フォーマット
- セッション開始時の環境セットアップ
- タスク完了時の通知
- 危険なコマンドのブロック

**注意点：** シェルスクリプトの知識が要ります。設定ミスでワークフローが止まることもあります。

## 迷ったら「4つの質問」で決める

新しい要件が来たとき、上から順に答えていくと選べます。

1. **外部のサービスやDBとつなぐ必要がある？** → Yes なら MCP
2. **イベントをきっかけに、必ず自動で走らせたい？** → Yes なら Hooks
3. **メインの会話を汚さず、別プロセスでやらせたい？** → Yes なら Sub-agents
4. **Claudeの知識・ルールを増やしたい？** → さらに細分化（下表）

| やりたいこと | 選ぶもの |
| --- | --- |
| 常に守らせたい | CLAUDE.md |
| 特定のファイルを触ったときだけ効かせたい | .claude/rules/ |
| 必要なときだけ読ませたい | Skills |
| 自分で叩いて実行したい | カスタムコマンド |

### グレーゾーンの例

「コードレビューの観点」をどこに書くか、という場合。

- いつでもレビュー観点を意識してほしい → CLAUDE.md
- レビュータスクのときだけ詳細なチェックリストを使いたい → Skills

正解は一つではなく、プロジェクトやチームの好みで変わります。

## デメリットと限界

**学習コストはそれなりにある**
7機能それぞれの役割と書き方を覚えるのは最初は骨が折れます。ただ、全部を一気に理解する必要はありません。まず CLAUDE.md から始めて、不満が出たら一つずつ足すのが現実的です。

**グレーゾーンは必ず出る**
特に Skills と Sub-agents の境目は曖昧です。「知識として持たせる」のか「別プロセスに投げる」のか。使いながら調整していくしかありません。

**設定ファイルが散らばる**
CLAUDE.md、`.claude/rules/`、`.claude/skills/`、`.claude/agents/`、`.claude/commands/`、`.claude/settings.json`……と置き場所が分かれます。プロジェクトが大きくなると管理が煩雑になりがちです。

## まとめ

7つの拡張機能は、**「いつ読み込まれるか」「誰が実行するか」** の2軸で整理すると迷いません。

| 機能 | タイミング | 実行者 | 一言で |
| --- | --- | --- | --- |
| CLAUDE.md | 常時 | Claude本体 | 全作業共通のルール |
| .claude/rules/ | 特定ファイル操作時 | Claude本体 | パスに紐づくルール |
| Skills | Claudeが判断 | Claude本体 | 必要なときだけ読む知識 |
| Sub-agents | こちらが依頼 | 別プロセス | 独立した作業場 |
| MCP | 外部連携時 | 外部サービス | 外部ツール・DBへの接続 |
| カスタムコマンド | 手動 | Claude本体 | 定型プロンプトのショートカット |
| Hooks | イベント発火時 | シェルコマンド | 決定論的な自動実行 |

迷ったら「外部連携？」→「自動実行？」→「別プロセス？」→「知識を増やす？」の順で考えてみてください。
